# T2, T3 and saved events

`casm_t2` decides which search candidates merit a dump. `casm_t3` turns those
dumps into figures and keeps the event records available to observers.

| Stage | Responsibility | Where to look |
|---|---|---|
| T1, hella | Search the beam streams for dispersed pulses. The deployed searcher since 2026-09-02 07:33 UTC is the `casm_hella_vishnu` fork, branch `vishnu-rfi`; candidate rates from before that date belong to `casm_hella_refactored`, the rollback target. Fork mechanism and live rates: casm-wiki `hella-vs-transientx.md`. Branch `hella-mask` of the fork adds optional flag-record output (not deployed, see [below](#hella-rfi-flags-and-the-schema-2-event-folder)) | Raw trial files and search status |
| T2, `casm_t2` | Combine trials, cluster on sky/time/DM, apply policy and request dumps | Clusters, trigger decisions and injection ledger |
| T3, `casm_t3` | Render candidate plots, archive detection-beam data, serve review pages | Event PNG, JSON, filterbank and web viewer; on branch `hella-mask` also a raw PNG, mask file, CSV tables and manifest |

The T3 viewer provides event review and injection statistics. Slack receives
candidate and injection results; the saved files and ledger let you inspect
them without searching chat history. See [the worked injection](../guides/injection-recovery.md)
first. Current service state and storage locations: casm-wiki `storage-map.md`
and `array-state.md`.

## Candidate Slack captions

New candidate posts link the candidate ID to
`http://localhost:8061/cands/<name>`, the monitor's event-detail page. The usual
SSH tunnel must be open on the reader's computer. The separate "Open in
dashboard" label is omitted to keep the caption short.

The caption shows UTC and Pacific event time. `America/Los_Angeles` selects
PST/PDT for the event date; a differing local date is shown explicitly. There
is no inserted line break, although Slack can wrap text in narrow windows.
Only `t3-collect` needs a between-pass restart to load this change; existing
messages and `.slack` markers remain unchanged. Caption tests cover summer,
winter, both DST transitions, date/year rollover and the 8061 link.
Source: `casm_t3` revision `330e2a9`, `tests/test_collect_caption.py`.

## Injection Slack routing

Since October 7, injection updates use `#injections`; on-sky candidate alerts
remain in `#candidates`. The injection-only channel ID is in
`~/.config/slack_channel_injections`. The shared `~/.config/slack_channel`
and token remain unchanged. Change routing between completed shots, because
existing message timestamps do not carry their original channel ID.

Replay is enabled for future recovered injections (`injection.replay.post:
always`, `on_miss: none`). Misses retain their outcome messages. Replay adds a
synthetic pulse to recorded background; the matched search cluster establishes
live recovery. The capture window was shifted earlier to cover recent measured
pulse leads. New live replay availability must be checked independently of the
configuration. Products remain in the existing event archive, with no new
retention policy. DM, width, S/N and cadence are unchanged.

Only the injection scheduler needs a restart to load replay settings. T2/T3
candidate workers and the monitor remain running; the monitor reads the same
SQLite ledger and saved artifacts. Historical Slack messages stay in the old
channel. The installed daily-report timer writes a local report, not a Slack
summary. Cutover and rollback steps are in `casm_t2/docs/operations.md`
(source revision `a577b94`).

## Where the results live

The database holds `clusters`, `triggers`, `gulp_stats` and `injections`
tables; the event archive of the running system holds each candidate's PNG, JSON record
and single-beam `.fil` (see the [injection tutorial's provenance section](../guides/injection-recovery.md#provenance)
for a worked path). The schema-2 folder that replaces this layout on deploy is
described [below](#hella-rfi-flags-and-the-schema-2-event-folder). Ordinary candidate archives keep the detection beam, not
every beam in the original dump. Injection archives contain a replay: the
synthetic pulse added to the recorded background. Those two filterbanks have
different meanings.

Since 2026-09-22 each trigger card carries a `gulp` block: every trial t2d
clustered for the event's gulp, each cluster's outcome, the rules applied and
the size caps that apply when a gulp is unusually large. t2d builds it from
the same clustering and decisions already recorded in the database, so it
changes no trigger decision. The candidate figure's bottom row reads this
block when present and falls back to the older per-candidate context panels
on cards written before it existed. Layout, units and truncation behaviour
are the casm_t2 schema, not restated here: see
[`docs/CARD_SCHEMA.md`](https://github.com/Coherent-All-Sky-Monitor/casm_t2/blob/main/docs/CARD_SCHEMA.md).
On branch `hella-mask` (not deployed) cards also carry a top-level `t2d_commit`, the
casm_t2 commit t2d runs from: `<sha>` (12 hex digits), `<sha>+dirty` when tracked files
differ from it, or `unknown`.

T3 collects corr2 event products onto corr1. Archive writing is fail-soft, so
a database row does not guarantee that every product exists. Raw dumps may be
deleted after plotting; do not promise that an old event can be rerendered. A
schema-2 folder can be rerendered from its `.fil` and `mask.npz` with
`t3-replot --event-dir` once the branch is deployed.
The event archive has no quota of its own and needs separate storage
monitoring.

## Read-only inspection

Use SQLite's `mode=ro` connection as shown in the tutorial. The convenience
function `casm_t2.db.connect` initializes and migrates the database, so it is
not the reader to use for an inspection-only session.

The existing modules provide the interpretation and plotting tools:

- `casm_t2.inject_outcome`: recovery categories and readable labels.
- `casm_t2.hella_kernel`: recovered trial widths in physical units.
- `casm_t3.dump_reader`: candidate intensity-dump loading.
- `casm_t3.single_pulse` and `casm_t3.plotting`: pulse analysis and figures.
- `t3-replot`: offline candidate rendering from a saved card. It reads the
  on-disk dump when the card still names one; otherwise, and for cards with
  no `dump_dir` at all (T2 backtest cards), it falls back to the archived
  single-beam `.fil` in the event directory (`--fil` names one explicitly,
  `--events-root ''` disables the fallback).
- `t3-replay-injection`: offline injection replay, adding the recorded synthetic
  pulse to a retained dump. This produces new diagnostics, not a live injection.
  `--clean hella`, on this tool and on `t3-replot`, first passes the beam through
  an offline copy of the deployed hella flagging stage (`casm_t3.single_pulse.
  hella_clean`: the static 470-484 MHz mask, per-gulp channel standardisation,
  the 0.2 s common-mode fit and the +-10 sigma clip, phased to hella's 8192-sample
  gulps) so the figure shows roughly what the search saw; the default is the
  data as recorded. `--scrunch T,F,SIGMA` (repeatable) adds hella-style
  SCRUNCH flagging stages to that cleaning for offline trials; the deployed
  search runs none. `--sumthreshold default` adds a SumThreshold stage against
  a channel-neighbour reference, which hella does not have (casm_t3
  `docs/architecture.md`, "Hella-like cleaning"). Since 2026-10-12 the two top panels' y axes start at -4
  sigma rather than 0, so the noise is visible. On branch `hella-mask` (not
  deployed) both tools can instead apply hella's recorded flags, which replace
  the offline replica (below).
  The injected parameters are written to the card JSON's `injection.summary`
  field, not to the figure title. For a recovered shot, t2d saves that gulp's
  block to `injection.gulp_dir` (`/mnt/nvme5/casm_pipeline/injection_gulps`,
  pruned after 14 days) and the replay draws the same bottom row as a trigger,
  every injection fragment in red; a shot with no saved block (T1 miss, shots
  before 2026-09-22) keeps the older bottom row.

Do not requeue live trigger cards to test a plot. That invokes the production
worker and its side effects. Starting injections, requesting dumps, posting to
Slack, changing configuration and deleting data require separate approval.

## Hella RFI flags and the schema-2 event folder

Built on branch `hella-mask` of casm_io (`357d3af`), casm_t3 (`240422f`), casm_t2
(`c9d1d86`) and the `casm_hella_vishnu` fork. **Not deployed.** The deploy swaps the
live hella binary on both nodes (an observation restart) and restarts the T2/T3
services, and waits for operator approval. Until then the running system behaves as
described in the rest of this page: candidate figures are drawn from the raw dump, the
event folder is schema 1, and no hella flag records or mask files exist. On deploy
this layout replaces the schema-1 PNG and JSON layout; the `.fil` is unchanged.
Design and rationale: casm-wiki `decisions/2026-10-13-hella-mask-figures-and-event-folder.md`.

Since 2026-10-12 hella searches data after SumThreshold flagging, but `t3-dump-plotter`
draws the figure from the raw dump, so the waterfall is the raw beam while the bottom
row is hella's own T1 output. The mask cannot be recomputed from a dump: hella's flags depend on
the whole 8192-sample gulp of a beam, while archived events span 0.57 to 1.19 gulps at
arbitrary phase. The offline replica (`--clean hella`) shared 96% of flagged bins with
the GPU stage on identical full gulps and omits uint8 quantisation. So hella records
its own flags, and T3 applies them.

### Figure pair

- `<event>.png`, posted to `#candidates`: hella's recorded flags applied. Every panel
  is computed from the unflagged cells (normalisation, band means, dedispersion and S/N
  use validity-weighted statistics). Flagged cells are grey; time
  with no flag record is hatched, so "unknown" differs from "flagged". The title ends
  `hella RFI flags applied`, with `(partial coverage)` when coverage is below 1 over the
  whole dump window. Without usable records the figure is the raw beam titled
  `hella RFI flags unavailable (<reason>)`. The bottom row (T1 trials of the card's gulp
  block) and the axes geometry are unchanged.
- `<event>_raw.png`: the same beam before flagging, posted as a thread reply to the main
  post. Its title ends `before hella RFI flagging; IB subtraction on|off|unknown`, read
  per event from the dump header (`BFCORR_SUB_INCOH`), never assumed.

The figure shows hella's flags applied. It is not a reproduction of the data hella
searched: hella's standardisation, baseline pass, 10 sigma clip and uint8 quantisation
are not reproduced, and the S/N is the figure's own, not hella's.

### Schema-2 event folder

`/mnt/nvme3/T3/EVENTS/<candname>/` on the node that made the dump; `t3-collect` mirrors
corr2's folders to corr1. The reader and byte-level layout are in
[casm_io](io.md#hella-rfi-flags-and-t3-event-folders).

| File | Content |
|---|---|
| `<candname>.png`, `<candname>_raw.png` | the figure pair |
| `<candname>.fil` | detection beam, single-beam float32 SIGPROC (unchanged) |
| `<candname>.mask.npz` | hella's mask aligned to the fil; absent when no record covered the dump |
| `<candname>.json` | summary, about 3 KB |
| `<candname>.t1.csv` | one deduplicated table of T1 trials around the event |
| `<candname>.clusters.csv`, `<candname>.beams.csv` | T2 clusters of the trigger gulp; alt/az of all 512 beams of the weights in force |
| `<candname>.manifest.json` | written last: every product with size and sha256 |
| `.slack` | posting marker written by `t3-collect` |

The summary keeps the card's top-level candidate names (the Slack caption and the
monitor read them) and adds `schema`, `width_ms`, `trigger` (including `n_gulp_dup`,
the other eligible clusters in the gulp, not dumped), `rules`, `storm`, `dump`,
`products`, `provenance`, `hella_mask` and `kind`. Provenance carries the observation
`UTC_START`, `weights_id`, the `t2d_commit` and `t3_commit`, the hella binary md5 and
flag configuration, `sub_incoh` and the UTC clock source. `kind` is `candidate` or
`synthetic_replay`. The card's `gulp.trials`, `gulp.clusters`, `context.members` and
`pointings` arrays are now the CSVs; `dump_dir` and `dump_files` are dropped because the
dump is deleted after plotting. `hella_mask.searched` says whether the search step that
ran right after flagging a gulp reached the beam. It is not per-sample search coverage.

A folder without a manifest is incomplete, and `t3-collect` does not post it. With
`--delete-dumps`, the dump is deleted after plotting only when the fil, both PNGs, the
summary and the manifest were written, and `mask.npz` too when the Slack figure has
hella's flags applied; otherwise the dump stays and the janitor ages it out. Existing folders are not
rewritten and there is no back-fill: events before the deploy have no hella record.

### Posting

`t3-collect` posts a schema-2 event once its manifest parses and agrees with the PNG
sizes on disk. The main figure goes first, then `<candname>_raw.png` as a thread reply
captioned "raw view, before hella RFI flagging". The `.slack` marker has one line per
post, `kind=main`, `kind=raw` or `kind=raw_unthreaded` (the raw figure posted as its own
message when the main post's timestamp did not resolve). The two posts are tracked
separately, so a failed reply is retried without reposting the main figure. Schema-1
folders keep their single-line marker and get no raw post.

### Commands and configuration

- `t3-dump-plotter --mask-records DIR` (default `''`, off) applies the records found
  by absolute sample index (the dump header's `OBS_OFFSET`); a dump that is not
  contiguous gets no mask.
- `t3-replot --event-dir <folder> --view masked|raw|both` re-renders a stored folder of
  either schema from its fil and mask. `--clean`, `--scrunch`, `--sumthreshold`, `--fil`
  and `--dump-dir` do not apply with `--event-dir`. A schema-1 folder has no mask, so
  the masked view is the raw beam labelled unavailable.
- `t3-replay-injection --mask-records DIR --raw-out PATH` draws a replay with the
  recorded flags applied at `--out` and the beam before flagging at `--raw-out`. Both
  titles say "synthetic replay": the pulse is added by the tool, and the records
  describe the live stream that carried the real injection. Without coverage,
  `--clean hella` keeps the offline replica, labelled as one. The card JSON gains
  `kind: "synthetic_replay"` and `hella_mask`.
- casm_t2 `injection.replay.mask_records` (default `''`, off) passes `--mask-records`
  to the replay command, which always gets `--raw-out`. The raw figure is posted as a
  reply in the shot's thread after the main figure, fail-soft and not recorded in the
  ledger.
- Every trigger card written by the branch's t2d also carries a top-level `t2d_commit`
  (`<sha>`, `<sha>+dirty` or `unknown`); see `docs/CARD_SCHEMA.md`.
- hella cfg keys, in `deploy/hella_extra.cfg`: `MASK_RECORD_DIR <dir>` (unset means
  recording is off) and `MASK_RECORD_CHUNK_GULPS <n>` (default 420, about one hour).
  Files are `<dir>/<UTC_START>/hmask_b<beam0>_g<gulp>_p<pid>.hmr`, one per stream per
  chunk. Recording runs off the search path: the GPU bit-packs the mask, a writer
  thread writes it, and hella drops a record and counts it instead of waiting. It
  refuses to record when a SCRUNCH stage could fire (the deployed one, 1e6 sigma, never
  does). Revert by deleting the line and restarting the observation. Details: fork
  `docs/MASK_RECORD.md`.

### Retention

hella does not delete its records. `t3-janitor --targets hella_masks` (run hourly on
corr1 by `t3-mask-janitor.timer`, never opening the T2 database) deletes closed chunks
older than 24 h (`--mask-max-age-h`) and enforces a per-node quota (`--mask-max-gb`,
default 100) on both nodes. A chunk a pending trigger card still needs stays, so a node
can sit over quota while pinned chunks alone hold it. An open `.hmr.part` untouched for
twice the age limit has no live writer and is deleted as an orphan unless pinned. The
pin rule assumes hella's gulp counter equals the absolute gulp number, which holds only
when `OBS_OFFSET` is 0 at attach; casm_t3 `docs/operations.md` says to confirm it against
the first deployed records. The design estimate is 1 to 6 GB per stream per day, too much
to keep indefinitely. Records are flat files, not a database.

### Deploy order

From casm_t3 `docs/operations.md`. Not yet run on either node.

1. casm_io `hella-mask` must be the checkout the services import: the plotter imports
   `casm_io.candidates.hella_mask` and `t3_event` at start, so an older casm_io fails
   every restart.
2. Create the records root, `/mnt/nvme4/data/casm/hella_masks`, on corr1 and corr2
   before hella writes and before the plotters get the flag. hella's `MASK_RECORD_DIR`,
   the plotters' `--mask-records` and the janitor's `--mask-root` must name the same
   directory on both nodes; a plotter pointed elsewhere labels every figure
   unavailable, and a janitor pointed elsewhere leaves the records unswept.
3. Restart the hella observation with `MASK_RECORD_DIR` set (check hella's startup line
   states `MASK_RECORD on`), then both `t3-dump-plotter` units (their unit files carry
   `--mask-records`), then `t3-collect`, then the injection scheduler. Deploy
   `t3-replay-injection` before the scheduler restarts on this branch's casm_t2, which
   passes `--raw-out` on every replay command; an older tool rejects it.
4. Install `t3-mask-janitor.service` and `.timer` on corr1, a deploy step with the hella
   recording.

After the first events, `hella_mask.coverage` should be 1.0, `hella_mask.gulps` 1 to 3,
and the plotter log free of `mask lookup failed`. To revert the figures, drop the
plotters' flag; no other state changes.

## Antenna layout and event geometry

October 6 metadata changes: the uploader supplies the product's geometry-based
widths before live events; the watcher uses the same nonzero-slot union helper.
Registry readers refresh changed product files, and T2 refreshes cached
clustering widths. Six stream associations must agree for an all-band pointing;
old incomplete histories now return unavailable rather than inferred geometry.
Embedded pointings in archived cards and existing Slack figures are unchanged.
These source changes require a T2/watcher reload; they do not deploy new weights.

Use `/home/casm/software/dev/antenna_layouts/current` for new-run array work.
An archived event's beam positions must come from the weights recorded as live
at its event time, not a recalculation using today's layout. Beam number alone
is insufficient to recover a historical sky position.

## Release contracts

T2 requires Python 3.11 or newer and declares Astropy for registry sky
coordinates. Pure width-veto, storm-shedding and occupancy functions live in
`casm_t2.candidate_policy`; the daemon retains compatible imports.

The candidate figure is layout v3 (approved 2026-09-22): a fixed 1510 x 1517 px
canvas, three-line title, and a bottom row that depends on whether the card
has a `gulp` block. Geometry is drawn from constants, never measured from the
data, so every candidate shares the same axes. `layout="legacy"` keeps the
pre-2026-09-03 figure. On branch `hella-mask` (not deployed) the v2 layout also takes
`mask=`, `coverage=` and `mask_label=`; with none of them the figure is drawn as before,
and the legacy layout rejects all three.

T3's reader orders segments by header time and numeric offset. It validates
each header, frame size, and time continuity before combining segments; gaps,
overlaps and incompatible formats raise errors rather than producing a spliced
time series. `sort_by_name=False` preserves a prevalidated caller order, but
does not disable format/continuity validation. Reads materialize selected beams
using memory maps rather than loading every beam's full payload first.

T3 declares its web dependencies, including FastAPI, Uvicorn, Jinja and form
parsing support. T3 and the monitor use explicitly configured
`casm_t3.web.event_store.EventStore` instances instead of patching shared web
module globals. Read-only connections do not initialize or migrate the database.

No automatic reaper runs for dumps, logs or the event archive; which T3
services are live and how storage is monitored is recorded in casm-wiki
`storage-map.md`, `array-state.md` and `incidents.md`.
