# T2, T3 and saved events

`casm_t2` decides which search candidates merit a dump. `casm_t3` turns those
dumps into figures and keeps the event records available to observers.

| Stage | Responsibility | Where to look |
|---|---|---|
| T1, hella | Search the beam streams for dispersed pulses. The deployed searcher since 2026-09-02 07:33 UTC is the `casm_hella_vishnu` fork, branch `vishnu-rfi`; candidate rates from before that date belong to `casm_hella_refactored`, the rollback target. Fork mechanism and live rates: casm-wiki `hella-vs-transientx.md` | Raw trial files and search status |
| T2, `casm_t2` | Combine trials, cluster on sky/time/DM, apply policy and request dumps | Clusters, trigger decisions and injection ledger |
| T3, `casm_t3` | Render candidate plots, archive detection-beam data, serve review pages | Event PNG, JSON, filterbank and web viewer |

The T3 viewer provides event review and injection statistics. Slack receives
candidate and injection results; the saved files and ledger let you inspect
them without searching chat history. See [the worked injection](../guides/injection-recovery.md)
first. Current service state and storage locations: casm-wiki `storage-map.md`
and `array-state.md`.

## Where the results live

The database holds `clusters`, `triggers`, `gulp_stats` and `injections`
tables; the event archive holds each candidate's PNG, JSON record and
single-beam `.fil` (see the [injection tutorial's provenance section](../guides/injection-recovery.md#provenance)
for a worked path). Ordinary candidate archives keep the detection beam, not
every beam in the original dump. Injection archives contain a replay: the
synthetic pulse added to the recorded background. Those two filterbanks have
different meanings.

T3 collects corr2 event products onto corr1. Archive writing is fail-soft, so
a database row does not guarantee that every product exists. Raw dumps may be
deleted after plotting; do not promise that an old event can be rerendered.
The event archive has no quota of its own and needs separate storage
monitoring.

## Read-only inspection

Use SQLite's `mode=ro` connection as shown in the tutorial. The convenience
function `casm_t2.db.connect` initializes and migrates the database, so it is
not the reader to use for an inspection-only session.

The existing modules provide the interpretation and plotting tools:

- `casm_t2.inject_outcome`: recovery categories and readable labels.
- `casm_t2.hella_kernel`: recovered trial widths in physical units.
- `casm_t3.dump_reader`: candidate intensity-dump loading.
- `casm_t3.single_pulse` and `casm_t3.plotting`: pulse analysis and figures.
- `t3-replot`: offline candidate rendering from a saved card and retained dump.
- `t3-replay-injection`: offline injection replay, adding the recorded synthetic
  pulse to a retained dump. This produces new diagnostics, not a live injection.

Do not requeue live trigger cards to test a plot. That invokes the production
worker and its side effects. Starting injections, requesting dumps, posting to
Slack, changing configuration and deleting data require separate approval.

## Antenna layout and event geometry

Use `/home/casm/software/dev/antenna_layouts/current` for new-run array work.
An archived event's beam positions must come from the weights recorded as live
at its event time, not a recalculation using today's layout. Beam number alone
is insufficient to recover a historical sky position.

## Release contracts

T2 requires Python 3.11 or newer and declares Astropy for registry sky
coordinates. Pure width-veto, storm-shedding and occupancy functions live in
`casm_t2.candidate_policy`; the daemon retains compatible imports.

T3's reader orders segments by header time and numeric offset. It validates
each header, frame size, and time continuity before combining segments; gaps,
overlaps and incompatible formats raise errors rather than producing a spliced
time series. `sort_by_name=False` preserves a prevalidated caller order, but
does not disable format/continuity validation. Reads materialize selected beams
using memory maps rather than loading every beam's full payload first.

T3 declares its web dependencies, including FastAPI, Uvicorn, Jinja and form
parsing support. T3 and the monitor use explicitly configured
`casm_t3.web.event_store.EventStore` instances instead of patching shared web
module globals. Read-only connections do not initialize or migrate the database.

No automatic reaper runs for dumps, logs or the event archive; which T3
services are live and how storage is monitored is recorded in casm-wiki
`storage-map.md`, `array-state.md` and `incidents.md`.
